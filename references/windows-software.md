# Windows 软件路线

## 接手现有构建

- 先读项目 README、构建脚本、配置、CI 和版本历史，确认支持的 Windows 版本与架构、现有安装器或便携打包方式、依赖与签名状态。沿用项目构建，不为发布资料改动无关业务功能。
- 依据项目已有流程构建，或用经核对的既有产物。将源码提交、程序版本、安装包版本、发行标签和附件命名对应起来。分别写明便携版和安装版的使用入口。
- 图从目标版本真实界面取材，优先展示一条核心操作路径。安装说明说清系统条件、取得哪一个包、首次启动与数据位置。只写已确认的兼容范围和真实签名信息。

## 候选与公开包验收

| 类型 | 适用检查 |
| --- | --- |
| 便携 ZIP | 核对结构，解压到新目录，启动真实 EXE，确认版本并跑一次核心操作 |
| EXE 或 MSI 安装包 | 核对字节和版本，在授权的测试环境安装，使用实际快捷方式或程序入口启动，执行核心功能 |
| 升级版 | 按项目已有升级规则准备旧版本和测试数据，核对升级后设置、数据与快捷方式。测试卸载时保留原用户数据边界 |
| 多平台或架构包 | 对照实际产物与构建矩阵，逐项记录哪些平台做了运行、哪些仅核验了附件 |

优先使用隔离测试目录、测试用户或可用的目标虚拟机。一次真实运行应有新输入与独立的输出目录，防止被旧产物掩盖。安装器退出成功后检查实际程序、日志和输出；没有授权或目标环境时完成可做的静态检查，并明确未运行的步骤。

例如 PDF 压缩软件，至少从下载得到的安装包启动目标版本，压缩一份公开或自制样例，打开新输出核对页数和可读性。若用户要求保留画质或引擎，按项目现有基准做对照，保持授权范围。仅核对哈希时结论限定为下载文件一致。

签名密钥、客户数据和私有调试文件只按项目既有流程管理。向用户报告签名、架构和安装验证证据，避免将已编译、可下载和已安装混写为同一状态。
