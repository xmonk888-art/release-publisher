# 功能变化与图文更新

用于 Skill 或软件的版本更新。先评估实际用户影响，再决定文案与图文的更新量；“重大”由使用方式和核心流程变化判断，不由版本号大小单独决定。

## 比较与范围

- 以已发布标签或可核实的上一版源码、介绍和附件为基线，对照候选源码、需求、测试记录及实际产物。证据不齐时标为未知，不把提交标题直接当成功能事实，也不为写发布介绍擅自开发功能。
- 在已有发布记录中列出重要变化、用户影响、证据、受影响正文/入口/图片、处理方式和验证状态。可以用简短表格；小修只需一两行，不强制额外维护一套台账。
- 仅获准准备或更新详情页时，不扩大到发布、安装或修改业务功能。尚未发布的版本、下载和 Release 链接标明候选；本地预览提供可用的本地附件和说明入口，不让计划中的地址看起来已经上线。

## 按影响选择更新方式

| 变化 | 默认处理 |
| --- | --- |
| 错误修复、内部实现调整，使用方式不变 | 更新版本说明，核对现有正文和图是否仍准确；准确则复用，不强制新增图片 |
| 新增独立能力 | 更新功能章节、适用场景和使用示例；文字不足以解释入口、操作或结果时增加对应图文 |
| 核心流程、交互、授权或完成判定变化 | 重写受影响流程及使用指令，更新相关流程图、操作截图或结果示例；不能只在旧图上改版本号 |
| 定位或主要能力发生变化 | 重新评估首屏标题、主图、核心能力展示和页面顺序，按实际需要重组，同时保留有效安装入口和未受影响内容 |

同一版本可混合以上类型，分别处理。旧图仍准确可保留；局部文案变化可局部修改；节点、分支或阅读关系改变时重构对应图。保留可编辑源稿，不随意重做无关品牌元素。

## 为读者解释新增功能

- 先写解决什么问题、何时使用、怎样启动、会得到什么结果，再选择表现形式。Skill 适合流程、分工、决策分支和交接示例；软件优先使用目标版本的真实界面、操作步骤和输出。专业操作细节仍遵循 [软件图文制作与验收](software-visual-guide.md)。
- 核心变化需要在功能正文中可找到，首页摘要负责概括并引导，Release 保留完整版本记录；不要把核心用法只藏在 Release，也不让新功能展示把安装入口挤到长页面底部。
- 展示失败修复、确认或停止条件时画出条件与去向，避免只画一条必定成功的箭头。示意图和软件截图区分；不把 Skill 规则写成后台常驻或保证永不停止。
- 有实测才展示实测：注明版本、日期、环境、输入范围、方法、结果和限制。合成样例明确标注；没有对照实验不宣称效率提升，没有真实运行不借用旧案例证明新功能已验证。
- 历史案例保留版本归属；新增能力有新证据时新增或修订对应案例，不能只给旧图换上新版本号。图文中的名称、数字与正文和证据一致。

## 验收与交接

- 逐项回查重要变化是否有对应正文、使用入口和适当展示；对“不改图”记录复用理由，防止遗漏，也避免无意义堆图。
- 检查中英文事实一致，桌面/手机的图、图注、阅读顺序和链接可用。图内文字可读、流程无歧义；关键说明也以正文提供，不仅嵌在图片中。
- 同步仓库主页、单技能/软件详情、更新摘要、Release 候选说明、发行包内介绍与图。ZIP 解压检查使用实际包内文件；历史归档不被覆盖。
- 完成时给出本次更新范围、实际预览/附件入口、对应证据及未验证项。仅做本地准备时明确尚未上传，正式上线检查留到获得发布授权后进行。
