# GitHub 发布与验收

## 先查真实目标

- 确认 owner/repo、仓库实际 ID 或来源关系、默认分支、现有远程提交、标签、Release、附件及写入权限。遇到仓库重命名，用仓库身份和重定向核对同一仓库，再把活跃下载入口更新为规范地址。
- 优先使用支持当前操作的 GitHub 连接器、现有 CLI 或官方 API。连接器的仓库权限字段和具体写入能力分别核对。收到 403 时检查实际账号与工具权限，换已有授权的接口；需要用户登录时走官方流程，等待授权确认后继续。
- 将源码、待发附件、私有检查材料分开。检查暂存文件与候选包清单，特别留意许可证、文档引用、系统要求、客户截图和本机绝对路径。凭证从已有安全配置获取，验证记录只写状态与公开标识。

## 执行与续作

1. 在本地准备提交、版本标识和可审阅的发布说明。仅更新资料时按用户授权的分支/PR方式提交。发行时让标签指向已核对的提交；发现不同提交或同名版本冲突时停在该冲突前，保留可完成的工作。
2. 可用时先创建 Release 草稿，附上候选文件，核对名称、字节数和 GitHub 返回的 SHA-256。发布后取得 GitHub 返回的正式页面与附件 URL。草稿附件可能使用临时地址，正式 URL 应在公开后再次核对。
3. 重试前查看分支、标签、草稿和附件现状。已一致的操作可复用；先诊断可恢复失败。涉及移动已公开的标签、删除或覆盖附件时按用户授权处理。失败状态写成“源码已提交 / 草稿已存 / 附件待上传”等具体状态。
4. 更新中英文首页的最新版摘要和安装入口。摘要紧跟首图并位于安装前，包含版本、关键变化、下载和完整 Release。没有首图时放在开头介绍后。检查旧下载入口与复制指令是否仍指向正确版本。

## 验收公开结果

- 在实际公开页面检查中英文介绍、安装区、链接、桌面和手机选图。验证最新版摘要位于首图与安装区之间，并核对下载与完整说明属于同一标签。浏览器失败时可取得 GitHub 渲染正文与公开资产回验；报告这一覆盖范围。
- 从用户可访问的公开 URL 实际下载附件，比较 SHA-256，检查 ZIP 和独立目录；如需验收安装或运行，按项目类型走对应路线。只有真实执行了相应操作才报告对应结论。
- 可在本技能目录运行 `python scripts/check_release_artifact.py <下载文件> --expected-sha256 <候选包哈希>`。检查 ZIP 时可加 `--extract-to <新目录>`，然后打开解压后的实际入口文件验收。
- 返回主页、说明、Release 和实际下载链接，以及版本、检查结果与需要继续验证的环境。保留可复用的文件清单和最小记录，使用新版本发布经批准的后续改动。

官方接口参考：[管理 GitHub Release](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository)、[Release REST API](https://docs.github.com/en/rest/releases/releases)、[附件 REST API](https://docs.github.com/en/rest/releases/assets)。
